---
title: Hyprland overrides
description: Customize the ARGVUS Hyprland configuration without editing packaged files.
---

ARGVUS supports two different ways to customize Hyprland. They must not be confused:

- `~/.config/hypr/hyprland.lua` is a complete user configuration. When it is valid and is not the stock Hyprland template, `argvus-start` launches Hyprland with this file instead of the packaged configuration.
- `~/.config/argvus/data/hypr/` contains incremental ARGVUS overrides. The packaged configuration remains the base and loads these fragments at the end.

For most customizations, use the incremental ARGVUS overrides. They keep the ARGVUS defaults, generated state and session integration available across package updates.

## Supported override files

Create the directory before adding a fragment:

```sh
mkdir -p ~/.config/argvus/data/hypr
```

The packaged configuration loads these files in this order when they exist:

```text
~/.config/argvus/data/hypr/monitors.lua
~/.config/argvus/data/hypr/rules.lua
~/.config/argvus/data/hypr/bindings.lua
~/.config/argvus/data/hypr/user.lua
```

Use the files by responsibility:

- `monitors.lua` — additional or replacement monitor declarations.
- `rules.lua` — window and layer rules.
- `bindings.lua` — additional keybindings or custom actions.
- `user.lua` — environment variables and other Lua configuration that does not fit the previous categories.

Do not edit `/usr/share/argvus/hyprland/config/hyprland.lua`. It is package-owned and can be replaced by an update.

## Environment overrides

Use `user.lua` for session environment values:

```lua
-- ~/.config/argvus/data/hypr/user.lua
hl.env("MY_VARIABLE", "1")
```

Environment changes affect applications started by the session. Log out and in again when the value must be inherited by the complete session; a compositor reload alone is not enough for applications that were already started.

ARGVUS owns `XDG_CONFIG_DIRS` and rebuilds it on every Hyprland reload, including reloads triggered by theme switches. Each ARGVUS configuration directory appears once, and entries inherited from the session are kept after them without repetition, so the value stays bounded. Sessions started by earlier versions may still carry the duplicated entries; if Kitty, `argvus-terminal` or `argvus --control-center` fail with `Out of buffer space calling sprintf`, log out and in again to start with a clean environment.

## Adding a keybinding

Use `bindings.lua` for a new binding that is not part of the ARGVUS keybinding manifest:

```lua
-- ~/.config/argvus/data/hypr/bindings.lua
hl.bind("SUPER + SHIFT + T", hl.dsp.exec_cmd("kitty"))
```

Use the ARGVUS Lua dispatcher helpers for compositor actions:

```lua
-- Focus the next window with a custom shortcut.
hl.bind("SUPER + CTRL + Tab", hl.dsp.group.next())
```

The binding is evaluated together with the packaged configuration. Check for conflicts with existing shortcuts before choosing a combination. Preserve the appropriate options when defining special bindings, for example:

```lua
hl.bind(
  "XF86AudioLowerVolume",
  hl.dsp.exec_cmd("wpctl set-volume @DEFAULT_AUDIO_SINK@ 5%-"),
  { locked = true, repeating = true }
)
```

The Control Center is the preferred way to change or disable an existing ARGVUS binding:

```sh
argvus-control-center keybindings
```

Those changes are stored canonically under `/keyboard_shortcuts` and materialized into `~/.config/argvus/data/generated/hypr/keybindings.lua`. A manually created binding in `bindings.lua` is not added to the Control Center manifest and is not managed by its restore action.

## Full native Hyprland configuration

`~/.config/hypr/hyprland.lua` is not an overlay file. If you create it, `argvus-start` validates it and uses it as the complete Hyprland configuration:

```sh
mkdir -p ~/.config/hypr
cp /usr/share/argvus/hyprland/config/hyprland.lua ~/.config/hypr/hyprland.lua
```

This approach gives full control, but the copied file becomes your responsibility. It can become stale as ARGVUS changes, and a custom file that omits the ARGVUS loader or generated-state handling can lose ARGVUS integration. Prefer the fragment files above unless you intentionally need a complete replacement.

The stock Hyprland file containing `AUTOGENERATED HYPRLAND CONFIG` is ignored by `argvus-start`, so its presence does not replace the ARGVUS configuration. A customized user file is selected only after validation; if validation fails, the launcher falls back to the packaged file.

## Apply and troubleshoot

After changing a Lua fragment, reload the session configuration:

```sh
argvus-sessionctl reload
```

Validate a complete Lua file before logging in again:

```sh
luac -p ~/.config/hypr/hyprland.lua
Hyprland --verify-config --config ~/.config/hypr/hyprland.lua
```

If the user configuration is rejected during startup, inspect:

```sh
grep -E "Hyprland Lua config|failed validation|using user Lua|fallback" \
  ~/.local/state/argvus/session.log
```

The packaged source and helpers are under `/usr/share/argvus/hyprland/`. Generated files under `~/.config/argvus/data/generated/` are derived state; edit the owning setting or override fragment instead of editing generated output directly.

See [Keyboard shortcuts](/docs/argvus-hyprland/keyboard-shortcuts/) for the Control Center workflow and [file locations](../../reference/file-locations/) for the complete configuration path reference.
